相同输入可产生不同输出。用相同 [context（上下文）](./Context.md) 跑两次 [model（模型）](./Model.md)，可能得到两个不同答案——有时差一个词，有时是完全不同的路子。你的代码什么都不用改，这就会发生。

这是模型生成文本的方式的属性，也是 [model provider（模型提供商）](./Model%20provider.md) 服务 [request（请求）](./Model%20provider%20request.md) 的方式的属性。[inference（推理）](./Inference.md) 期间，模型对可能的下一个 [token（词元）](./Token.md) 产出一个概率分布，再从其中采样一个——通常故意带点随机，因为总挑最可能的 token 会产出重复、低质的文本。回答开头一个采样不同的 token 会改变其后所有 token，一个不同的词就是这样变成完全不同的路子的。provider 侧的服务再叠上更多变数：请求在共享硬件上被批量调度，批次间极小的浮点差异可能翻转两个 token 之间接近的胜负。没有一个开关能全关掉。

对 [agent（智能体）](./Agent.md) 在同一任务上，要预期结果有分布。多数响应落在合理质量钟形曲线内——非确定性因此还能忍——但尾部是真的：有些日子模型显得敏锐，有些日子像丢了主线。同一任务，不同的掷骰。两个实际后果。重试是正当策略：一次失败只是分布中的一次抽样，同一任务的新尝试可能就抽得更好。而且验证比对确定性工具更要紧——你不能测一次 agent 行为就指望它重复，所以 [automated check（自动化检查）](./Automated%20check.md) 必须兜住坏的抽样。

小心别过度叙事化。人是模式匹配机器，一连串坏运行会显得像"模型这周变差了"的证明。通常只是分布。

_用法：_

"Claude 今天烂透了。他们发了更差的版本吗？"

"多半没有——模型输出是非确定性的。同一任务你就会有好日子坏日子。明天再试，然后才去找原因。"
